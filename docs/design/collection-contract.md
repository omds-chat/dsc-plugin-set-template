# 合集契约:骨架、标识与证书边界

本文件说明 dsc 插件合集骨架的契约:骨架里放什么、合集 id 从哪里来、终端签名证书按什么顺序解析、构建与校验各自负责什么,以及本仓库与使用方仓库之间的分工。

操作步骤不在本文复述。怎么复制骨架、怎么准备签名材料、怎么在临时仓库里试跑,见 [README](../../README.md);合集目录里的文件清单见 [template/plugins/README.md](../../template/plugins/README.md);JSON 字段与脚本校验的对应关系见 [schemas/README.md](../../schemas/README.md)。本文只讲这些做法为什么这样定,以及边界落在哪里。

## 1. 各份文档回答什么

| 文档 | 回答的问题 | 不回答的问题 |
|:---:|:---:|:---:|
| [README](../../README.md) | 怎么把一个合集做出来:步骤、命令、开关 | 为什么这样定、什么不该做 |
| [template/plugins/README.md](../../template/plugins/README.md) | 合集收录什么:目录层级与必需文件 | 骨架之外的工程从哪来 |
| [schemas/README.md](../../schemas/README.md) | 每份 JSON 的形状,以及它对应哪条脚本校验 | 判定失败时该改哪一侧 |
| 本文 | 取舍与边界:为什么这样定、哪里不能越界 | 具体命令与字段清单 |

三者的优先级是固定的:脚本是权威实现,Schema 是书面契约,文档是解释。三者冲突时按这个顺序修文档与 Schema,不改脚本去迁就文档。

## 2. 合集骨架的职责

### 2.1 骨架是数据布局,不是可运行的工程

`template/` 只装合集数据本身:根目录的几份 JSON、`certs/` 的目录结构、`plugins/` 的三层目录。`scripts/`、`schemas/`、`.github/` 与 `package.json` 故意留在骨架之外,使用方建合集时另行取走。

这样切分的理由有三条。

| 理由 | 说明 |
|:---:|:---:|
| 骨架会被整体接管 | 复制之后,骨架里的文件就是该合集自己的数据;工具链若跟着复制,会从"模板维护者的工具"变成"每个合集的私有副本",副本各自演化后校验语义必然分叉 |
| 两者修改节奏不同 | 骨架随分发规范变,工具随实现变;绑在一起会让规范改动被实现细节拖住 |
| 归属清晰 | 工具出问题找模板,数据出问题找合集,不需要先判断是哪一半坏了 |

由此产生一条明确的边界:骨架不承诺"复制出来就能跑"。能跑的前提是使用方把工具链一并组装进自己的仓库,那是使用方的组装动作,不是骨架的内含能力。

### 2.2 骨架只放占位文件,不放证书

| 位置 | 骨架里的内容 | 理由 |
|:---:|:---:|:---:|
| `certs/<合集 id>/` | 一个占位文件 | 真实证书属于具体合集,不属于骨架 |
| `certs/` 下的其他来源目录 | 无 | 来源按合集的实际情况增加,骨架不预设 |
| 根目录 JSON | 空值或初值 | 结构可以固化,取值必须由合集决定 |
| `plugins/` | 作者清单与说明 | 收录内容属于合集 |

证书绝不进骨架,理由不是"怕泄露私钥",而是三条更根本的:

- 证书是签发方对**某一个具体主体**的声明。骨架没有主体,它既不是某个合集,也不代表某个运营者。把证书放进骨架,等于给一个抽象模板安上具体身份。
- 骨架会被复制任意多次。证书一旦随骨架流出,所有副本共享同一身份与同一信任锚,签名就再也无法区分"这是谁签的"。
- 骨架里没有、也不该有配对私钥。没有私钥的证书签不了名,只会制造"看起来已经配好了"的假象,而假象比缺失更难发现。

因此占位文件承担两件事:占住路径,以及提供一个机器可识别的不合格状态。路径这件事不是形式主义——文件名与所在文件夹都由合集 id 推导,占位文件把"这个位置长什么样"写成了可复制的事实,而不是文档里的一句描述。状态这件事同样重要:它让"证书还没就位"成为一个有名有姓的判定结果,而不是模糊的"找不到文件"。

占位文件既不是预填的默认证书,也不是临时测试证书。它是状态标记:位置已就位,内容未就位。文件名本身也承担表达职责:一句可读的指令,加上全大写与下划线包围,既让复制的人不必翻文档就知道要替换,也保证它不可能与真实证书同名。

### 2.3 骨架不收录内容

骨架里没有插件、没有作者公钥、没有标签取值。若骨架带示例内容,使用方要么删掉、要么误留;两种结果都会把"示例"变成事实上的收录。空骨架逼着使用方对每一条收录做一次显式决定。

## 3. 合集 id 的推导顺序

合集 id 是路径片段,决定终端签名证书的文件夹名与文件名。它是推导出来的,不是声明出来的,顺序固定为三档。

| 顺序 | 来源 | 为什么在这一档 | 典型场景 |
|:---:|:---:|:---:|:---:|
| 1 | 显式指定的合集名 | 唯一由人说了算的入口,也是唯一能纠正后两档的手段 | 目录名与合集名不一致、临时副本、需要固定 id 的自动化 |
| 2 | 分发目录 `build-info.json` 的 `collection` 字段 | 分发目录里没有可信的目录名,目录名只是输出目录名;这个字段是构建当时写下的自我记录 | 对分发目录再做一次校验 |
| 3 | 合集目录名 | 新建合集的自然来源,不需要任何额外输入 | 源码仓库根目录 |

顺序不能反过来,原因在每一档的稳定性上:目录名最不稳定(checkout 目录、临时副本、输出目录都可能不叫合集名),分发记录是构建产物但只存在于分发目录,显式指定则是唯一能覆盖前两者的输入。产物优先于猜测,显式优先于产物。

由此得到一条一致性要求:id 参与路径,不参与内容。它不写进任何清单,也不写进合集元数据。写进去就多出一份需要与路径同步的真相,而路径本身已经能表达它。

边界与风险:

- 三档都可能"成功"推导出一个能跑、但不是想要的那个 id。所以任何与 id 相关的报错都必须点名它的来源(显式指定、分发记录、目录名),否则改错地方会越改越乱。
- 改 id 等于搬证书。证书所在文件夹与文件名都取 id,旧路径上的证书不会自动跟随。
- 分发记录损坏时静默退回目录名,不报错。它由构建流程生成,不是签名输入,为它阻断校验得不偿失。

## 4. 终端签名证书的三档解析

| 档位 | 路径 | 语义 | 命中后的处理 |
|:---:|:---:|:---:|:---:|
| 1 | `certs/<合集 id>/<合集 id>-eec.crt` | 现行布局,真实证书唯一允许的位置 | 按证书解析,并做证书链、有效期与用途检查 |
| 2 | `certs/<合集 id>/_REPLACE_THIS_FILE_AS_YOUR_EEC_` | 骨架占位文件:位置已就位,内容未就位 | 不当证书解析,只给出替换提示 |
| 3 | 根目录 `eec.pem` | 旧布局,仅为尚未迁移的合集保留 | 按证书解析,同时给出迁移提示 |
| 无 | 三个位置都不存在 | 解析失败 | 由调用方按各自语义报错,解析本身不抛错 |

三条排序理由:

- 第一档先于第二档,因为"换了证书但忘了删占位文件"是最常见的中间状态。真实证书必须胜出,否则一个已经合法的合集会被自己的残留文件判成不合格;残留本身另有独立提示,两件事不混在一条判定里。
- 第二档先于第三档,因为占位文件是"新布局尚未就绪"的显式声明,优先级高于兼容回退。若回退排在前面,一个同时留着旧证书的目录永远看不到"这里要换证书"的提示,骨架就会永远停在"合法但不合格"的状态。
- 第三档只能放最后,因为它是兼容,不是路径。新合集不得使用,方向是删除。

占位语义为什么是三态而不是异常:解析结果同时给出"有没有命中""命中在哪一档""命中的是不是占位"。调用方据此各自决定——签名入口直接拒绝,校验在骨架模式下把这一条降级,构建在需要签名时拒绝,其余检查继续跑完。若解析到占位就抛错,一次只能报出一个问题,骨架也永远跑不完一条完整校验。这是"一次性汇总全部问题"这条总取舍的一部分。

占位文件永远不进证书链,也不做有效期与用途检查。它不是证书,送进 X.509 解析只会得到一条难读的解析失败,替代不了已经给清楚的替换提示。证书相关的检查在占位命中时退化为"无法校验",而不是崩溃。

三档全空时不抛错,只报告三个候选路径都不存在,再由调用方按语义决定报错还是降级。理由同上:解析层负责回答"有没有",判定层负责回答"算不算错"。

旧布局为什么留着,以及它的代价:留着是为了让尚未迁移的合集继续可校验、可分发。代价是解析多一档、分发多一条复制规则、文档多一段兼容说明。所以它被标注成回退而不是别名:只出现在解析顺序的最后,只出现在提示里,新合集不得使用。

边界:解析只回答"从哪里读证书",不回答"这张证书可不可信"。可信由根证书链决定,解析成功而链校验失败仍然是失败;反过来,解析失败也不代表合集内容有问题。

## 5. 构建与校验的职责

| 关注点 | 校验 | 构建 |
|:---:|:---:|:---:|
| 读还是写 | 只读,不改任何文件 | 写:生成清单与签名,写分发目录 |
| 判定什么 | 结构与签名是否自洽 | 产物是否完整、是否需要重新签名 |
| 失败之后 | 报告全部问题,不留下痕迹 | 不产出分发内容 |
| 入口关系 | 可独立运行 | 先写完清单与签名,再调用同一份校验,通过后才写分发 |

为什么共用同一份校验实现:两套语义必然分叉。构建若自带一套"我刚写了什么所以一定没问题"的判断,校验就抓不到构建的错。共用之后,构建的成功判据就是校验的成功判据,不存在第二种合格定义。

为什么构建先写后校验:清单与签名是产物的一部分,只能由写操作产生,但必须通过只读判定才算数。顺序固定为:签名产物本体、生成三层清单、校验、写分发。校验不过就停在校验,分发目录里不会出现半成品。

写操作的两条自我约束:

- 层版本号只在该层文件集合或内容变化时加一,不变时沿用。这样"重跑一遍构建"不会产生无意义的版本漂移。
- 内容变了却没有可用的签名私钥时,删除已失效的旧签名,而不是留着它。留着等于分发一份必然验不过的清单,比缺签名更坏:缺签名是明显的缺,失效签名是伪装成完整的缺。

骨架模式的开关位置:降级是入口参数,不是校验逻辑内建的行为。降级只对骨架成立,对真实合集是放水。把开关放在入口,使用方看得见自己在放宽哪一条;真实合集的 CI 不打开它,占位文件没换掉就是错误,而不是警告。

校验与 Schema 的分工:脚本是权威实现,Schema 是书面契约。Schema 不参与运行时判定,它描述的是同一套约束的另一种写法。两者必须同步修改,否则会出现"文档允许、脚本拒绝"或"脚本放过、文档禁止"。

边界:

- 构建不判断内容质量。插件写得好不好、标签取得合不合适,不在构建的判断范围内。
- 校验不改文件。它发现问题只报告,修不修、怎么修由人决定。
- 分发目录是投影,不是第二份真相。源码与签名才是真相;对分发目录再跑一次校验,是为了确认投影没有失真。
- 根证书不进分发。它由另一条渠道分发,客户端用内置指纹核对,合集不承担分发根证书的职责。

## 6. 模板与使用方

本仓库是契约载体,不是合集。它对外发布规范与 Schema,但不发布任何合集,也不产生任何签名。

| 使用方 | 从模板拿走什么 | 自己保留什么 | 不与模板共享什么 |
|:---:|:---:|:---:|:---:|
| awesome 系插件合集 | 骨架布局与校验语义 | 内容、证书、CI 配置 | 工具链副本可以自行演化 |
| 人类化资产合集 | 不取本模板的骨架 | 资产骨架与产物形态 | 不与插件合集共享目录内容 |

### 6.1 awesome 系插件合集

它们是合集,复制骨架之后接管全部数据;工具链可以整份取走,也可以按自身需要重写。

唯一不可分叉的是校验语义:证书三档解析顺序、清单覆盖范围、签名格式。这些一旦分叉,同一个文件在两个仓库会得到两种判定,而使用方无从判断该信哪一份。所以规则是单向的:先改模板,再同步到合集。

模板对它们不承担三件事:不代持证书,不代为签名,不替它们判断收录什么。

### 6.2 人类化资产合集

资产合集的产物是资产包,不是插件脚本;它有自己的规范来源与骨架,本模板不覆盖资产内容。

两者的关系是"同一类对象、不同产物家族":都叫合集,都有合集 id、都有终端签名证书、都可以分发,但不共享目录布局与产物类型。因此本模板对资产合集只承担一条边界责任——不把资产包塞进插件目录的三层结构里。三层的每一层都围绕"作者、插件、版本"与插件脚本的签名对象定义,资产包套进去只会得到一个名不副实的目录树。

是否复用本仓库的校验语义,见第 7 节。

### 6.3 模板的三条不做

- 不收录内容:模板仓库永远没有插件、作者与标签取值。
- 不持有证书:仓库内只有占位文件,真实证书由根 CA 侧签发并保管。
- 不代为签名:签名发生在使用方的 CI,私钥只从 CI secret 读取,仓库内不存放任何私钥。

## 7. 未定稿

以下四件事尚未定稿。已确定的边界与已排除的选项一并列出,避免同一个问题被反复讨论。

### 7.1 旧布局回退的删除时点

已定:新合集不得使用根目录的 `eec.pem`,方向是删除。

未定:何时删除,以及删除前是否需要给尚未迁移的合集一个强制期限。

已排除:

- 永久保留。代价是每条解析路径都带一段兼容分支,而这段分支永远不会再被新合集走到。
- 立刻删除。会让未迁移的合集在校验阶段直接失败,没有过渡窗口。

### 7.2 资产合集是否复用本仓库的脚本与三层清单

已定:本模板的骨架只服务插件合集。

未定:资产合集是把本仓库的校验语义取过去,还是另起一套。

已排除:把资产包直接放进 `plugins/` 的三层结构。产物不是插件脚本,版本目录的签名对象与 L3 的覆盖范围都不成立,硬套等于把插件语义当成通用语义。

### 7.3 分发目录里残留占位文件的处理强度

已定:有真实证书而占位文件仍在时给出提示;构建会把整个 `certs/` 目录复制进分发,残留的占位文件因此会一起被分发。

未定:这条提示是否升级为错误。

已排除:构建时静默跳过占位文件。那会让分发目录与源码不一致,客户端拿到一个残缺的证书目录,而问题在构建日志里看不到。

### 7.4 合集 id 的来源是否增加第四档

已定:三档,顺序固定。

未定:是否还需要从别处读 id。

已排除:

- 从合集元数据读。那会多出一份必须与路径同步的真相,而路径已经能表达它。
- 从 git remote 推导。一个仓库可以有多个 remote,CI 里的 remote 形态也不保证,推导结果不稳定。
